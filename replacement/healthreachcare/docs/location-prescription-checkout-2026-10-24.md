# Saved location, pharmacy pricing, uploads and checkout — 24 October 2026

## Changes

- Replaced the coordinate-only address editor with a controlled, prefilled address form. A permitted device position can populate street, suburb, city, province and postcode through reverse geocoding. A manually entered address can be searched to place a pin; ambiguous results require selection. Changing street fields clears stale coordinates. Existing saved Home addresses are reused across the account and medication/homecare checkout. An explicit change to an unpaid medication checkout updates its address without overwriting its products or prices. Paid checkouts cannot be changed through this action.
- Added an authenticated `/api/location` adapter for Geoapify forward/reverse geocoding. The key stays server-side. Requests share no medication, clinical or identity-document information. User confirmation is explicit in the lookup action. Country validation, bounded inputs, timeout, generic errors, per-user limits and atomic application quota prevent unrestricted use. No IP-derived location or fabricated street address is supplied.
- Added actual premises coordinates to provider service profiles for nearest-provider matching. The user must confirm that the captured location is the business premises. Distances are straight-line distances, not road estimates or delivery guarantees.
- The real patient catalogue preserves each pharmacy's actual product price and description. Equivalent configured name/strength/form/pack/Rx keys are grouped for comparison. Available offers are ranked by stock, opening status and actual saved proximity where known. Different-price offers are not silently substituted. A basket contains products from one pharmacy; the server validates stock, ownership, eligibility and current price again before payment. Unknown distance is identified rather than invented.
- Prescription uploads now expose prescription, ID front, ID back and selfie controls before an order exists, and in the saved order's document step. Saved identity documents can be explicitly linked to the patient's own draft. Uploading/linking does not rewrite selections, quantities, address or totals, and never approves or submits automatically. Pharmacy review and identity verification still precede payment/fulfilment.
- Added one explicit account-policy acceptance action that records individual current-version acknowledgements as a bundle. Repeating acceptance is idempotent. Saved acceptance applies across the account. Optional marketing/device-location choices remain separate; manual addresses are not forced to opt into device location. Existing acceptance history remains intact.
- Connected authenticated private provider/driver documents, support/appointment evidence and existing contextual attachment/voice-note storage to the same Cloudflare R2/D1 workflow. Fixed attachment downloads to use Firebase authorization for real accounts. Supported formats and per-feature limits are retained. Clinical attachments are unavailable in driver coordination channels; text coordination remains available. All sends require a persisted acknowledgement. Existing completed conversations remain archived and permission checked.
- Added email and WhatsApp support links to account support, help articles, service cases and payment review. Medical/identity documents should be uploaded in the app rather than through those external channels.
- Added a detailed payment review: provider, patient, service, schedule where relevant, medication line quantities/unit prices, address/unit/instructions, subtotal, platform delivery fee, discounts and saved final total. Only payment processing remains simulated; no card/bank details or real charge are requested. Existing records are genuine application records, not seeded providers or orders.

## Required external setup — address autofill is not live yet

No `GEOAPIFY_API_KEY` was present in the existing Cloudflare Worker bindings. The code returns a clear setup/unavailable state rather than pretending lookup succeeded. Device coordinates and manual addresses can still be saved.

Create a Geoapify Free project, then add its API key as a **secret** named `GEOAPIFY_API_KEY` on the existing `healthreachcare` Worker. Add the same secret through Sites environment settings only if address lookup is also needed on the separate Sites publication. Do not put the key in source code, a public frontend variable or chat. No DNS/Firebase changes or new database are needed. Existing `keep_vars` configuration preserves secrets on later deployments.

The adapter caps each deployment at 1,000 outgoing lookups per UTC day and 40 per user/day, with request spacing. These caps do not account for use of the same key by other apps. Keep the provider account on its Free plan and review its current quota/terms. Never enable a paid upgrade automatically. Geoapify's pricing page currently states Free availability without a credit card and permits production use subject to its quota and attribution requirements.

Sources consulted: https://www.geoapify.com/pricing/ ; https://apidocs.geoapify.com/docs/geocoding/forward-geocoding/ ; https://apidocs.geoapify.com/docs/geocoding/reverse-geocoding/ . The public Nominatim service was deliberately not added as an automatic patient-address lookup service; its usage/privacy policy is at https://operations.osmfoundation.org/policies/nominatim/ .

## Validation and limits

New tests cover address mapping, authenticated lookup, input/consent/country checks, quotas and key secrecy; device/manual form handlers with mocked location/provider responses; reusable identity uploads and private downloads; explicit policy-bundle persistence and unchanged optional preferences; unchanged prescription selections; saved/changed checkout addresses and unchanged totals; pharmacy-specific comparison/proximity; support evidence; PDF, PNG, WebM and Ogg file persistence/access.

The repository's full API/navigation/views/logout/interaction/account suite, lint, TypeScript and production build must pass before publication. Automated tests use fictional in-memory records and mocked Firebase/geocoder responses. No real customer order, medical upload or notification is created by these tests. Real camera/microphone playback, live signed-in upload and live geocoder accuracy require interactive verification and are not claimed tested.

Existing accounts, documents, orders, authentication project, payment configuration, administrator policy and DNS are preserved. No paid integration is enabled.
