# Main administrator and Cloudflare handoff

The selected Firebase project remains gen-lang-client-0810450473. Main-admin access is pinned by the server-side HRC_MAIN_ADMIN_UID setting to the existing owner's UID, resolved from the app's own saved account. It is not granted to the first public signup, an email pattern, a client role or a URL parameter. Sites runtime revision 3 stores the selected UID as a secret; account passwords and Firebase users are not changed.

The first registry creation is atomic in the existing D1 workspaces table and records the configured main UID. Once created, the persisted registry is authoritative: later deployments with the initial bootstrap UID cannot overwrite a completed ownership transfer. Only the main administrator may grant or revoke other administrators. Each target must already have a registered account; no password or fake invitation is created for them. Every admin request checks the current Firebase account and verified-email state. Administrator membership and provider permissions remain separate from public signup selections.

Sensitive admin changes require an actual Firebase auth_time within five minutes. Password or Google reauthentication refreshes that authentication proof. Password-reset emails use the existing Firebase service. Email verification establishes ownership of the email address; resending a verification email is not implemented as a second login factor or claimed as MFA. Root recovery uses Firebase account recovery for the same UID; there is no public ownership-reset shortcut.

Ownership transfer is initiated only by the current main administrator, requires typing their UID, targets an existing administrator who has opened their verified account, expires after 24 hours and requires the nominated administrator's fresh authenticated acceptance. The old main remains in charge until acceptance and then becomes a delegated administrator. An unrelated admin cannot transfer ownership, remove the main admin or accept another person's pending transfer. Actions have a persisted audit history and compare-and-swap writes.

Admin sign-in routes to the existing Admin dashboard; its Account control opens administrator management at /account. Patient navigation and existing service-card/Homecare/order changes are preserved. The admin dashboard has no bottom navigation.

Checks: 28 registry/authorization/transfer/revocation tests, 11 admin HTTP boundary tests and the existing real-account/document suites passed using fictional isolated records. Full regression, lint, TypeScript and production build results are reported after execution. A real owner login/reauthentication still requires the owner's browser; no credentials or recovery email were entered or sent by the agent.

Cloudflare CLI whoami still reports unauthenticated. No shared Cloudflare browser login has succeeded. GitHub main still selects the old app; PR #8 prepares the replacement and rollback. The user's Cloudflare DB/R2 bindings and D1 table were confirmed by their pasted dashboard output, not by current direct account access. The Sites environment is separate from the user's own Cloudflare environment: HRC_MAIN_ADMIN_UID and the new Firebase authorized production domains must be set there before activation. Existing Sites D1/R2 records must be preserved and their transfer/access checked before claiming a complete live cutover. No Cloudflare/DNS/deployment settings were changed by this work.
